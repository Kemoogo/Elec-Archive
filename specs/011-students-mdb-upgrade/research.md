# Research & Architectural Decisions: ترقية منظومة شئون الطلاب واستخراج ملفات Access (.mdb)

**Feature**: `011-students-mdb-upgrade`
**Date**: 2026-11-04
**Domain**: استخراج بيانات قواعد بيانات Microsoft Access (.mdb) داخل بيئة Node.js / Linux معزولة (Air-gapped)

---

## 1. محرك قراءة واستخراج ملفات Microsoft Access (.mdb) في Linux

### القرار (Decision)
استخدام أدوات النظام الأصلية `mdbtools` (`/usr/bin/mdb-export`, `/usr/bin/mdb-tables`) عبر وحدة وسيطة آمنة ومكتوبة بـ TypeScript في `next/lib/students/mdb-parser.ts` تستدعي `child_process.spawn` أو `execFile` لمعالجة ملفات `.mdb` وتحويل جداول `src_soldiers` و`gyabhabs` إلى مصفوفات كائنات منظمة (Structured Objects) مع فحص الترميز (Encoding) باللغة العربية (Windows-1256 / UTF-8).

### الأسباب (Rationale)
1. **الجاهزية والتوافق المحلي الكامل:** أداة `mdbtools` (`mdb-export` و`mdb-tables`) مثبتة بالفعل محلياً في بيئة النظام (`/usr/bin/mdb-export`)، وتعمل بسرعة فائقة في قراءة ملفات Jet 3/4 Access دون الحاجة إلى تثبيت أي حزم خارجية أو اتصال بالإنترنت (متوافق 100% مع مبدأ Offline-First).
2. **عزل الأداء والأمان:** استدعاء `mdb-export` كعملية فرعية معزولة (`spawn`) بقراءة مجزأة (Streaming/Buffer) يحمي خادم Next.js من تسريب الذاكرة أو تعليق الـ Event Loop أثناء معالجة آلاف السجلات.
3. **الترميز العربي (Arabic Character Support):** تدعم `mdb-export` معلمة `-R` و`-d` وخيار الترميز لضمان قراءة الأسماء الرباعية والمحافظات والعناوين العربية بدقة دون تشويه الحروف.
4. **الاعتمادية في بيئة Docker / Linux:** تتيح إضافة بسيطة لـ `apt-get install -y mdbtools` في الـ Dockerfile استمرارية العمل على أي سيرفر أو حاوية بدون إعدادات معقدة.

### البدائل التي تمت دراستها (Alternatives Considered)
- **مكتبات Node.js نقية مثل `node-adodb` أو `node-mdb`:** تعتمد على حزم Windows OLE DB / COM Objects أو Python C++ bindings ولا تعمل بمرونة داخل Linux containers بدون تبعيات ضخمة مثل Wine.
- **مكتبة `mdb-reader` (JavaScript pure):** تدعم فقط بعض إصدارات Access القديمة وتواجه مشاكل حادة في قراءة النصوص العربية (Windows-1256 codepage) وجداول الحبس المتداخلة.

## 2. استراتيجية التحديث الذري والمطابقة (Upsert Strategy)

### القرار (Decision)
اعتماد الرقم العسكري (`militaryNo` أو `studentId`) كمفتاح فريد قطعي (`unique index`) في مجموعة الطلاب `students`. عند تأكيد استيراد ملف `.mdb`:
- يتم تنفيذ عمليات الحفظ باستخدام `Student.bulkWrite` بنمط `updateOne({ militaryNo }, { $set: updateFields, $setOnInsert: insertFields }, { upsert: true })`.
- حماية السجلات المشطوبة: إذا كان الطالب مشطوباً مسبقاً (`status: "transferred_personnel"` أو `isStriken: true`)، يتم تحديث بياناته الشخصية والاتصال فقط، ويُمنع نهائياً إعادة تفعيل حالته أو مسح بيانات الشطب والتصديق.

### الأسباب (Rationale)
1. **السرعة والذرية:** تنفيذ 2,000 طالب عبر `bulkWrite` يستغرق أقل من 300 مللي ثانية على MongoDB المحلي، مقارنة بحلقات الحفظ الفردية البطيئة.
2. **منع التكرار تماماً:** الرقم العسكري فريد على مستوى القوات المسلحة، ومطابقته تضمن استقرار قاعدة البيانات حتى لو تم رفع الملف عدة مرات.

## 3. محرك التمام اليومي للطلبة وقاعدة الإغلاق عند 06:00 صباحاً

### القرار (Decision)
بناء موديل مستقل `StudentRollcall` يتبع نمط اليومية العسكرية:
- التمام يُجهّز في المساء لليوم التالي (`targetDate = tomorrow`) ليمثل وضع القوة صباح باكر.
- الحالات: `draft` (مسودة) ← `approved` (معتمد) ← `closed` (مغلق نهائياً).
- قاعدة الإغلاق عند الساعة 06:00 صباح يوم التمام تُفرض على مستوى الـ API (Server-side validation) بمقارنة التوقيت المحلي للخادم. أي محاولة حفظ بعد 06:00 لغير الـ Admin تُرفض بكود 403 مع رسالة خطأ واضحة.
- عند تعديل الـ Admin بعد الإغلاق، يلزم إرسال حقل `overrideReason` ويسجل ذلك في الـ `AuditLog` فوراً.

### الأسباب (Rationale)
1. **التوافق التام مع انضباط المنظومة العسكرية:** التمام وثيقة قيادية حساسة تُرفع للقائد العام صباحاً؛ إغلاقها عند 06:00 يضمن ثبات الأرقام ويمنع التلاعب بأثر رجعي.
2. **تجهيز الوضع المسبق:** الوحدات العسكرية تضع التمام في المساء (بعد طابور السير أو التفتيش المسائي) ليكون جاهزاً للاعتماد عند طابور الصباح.

## 4. بنية التبويبات والمراحل (FolderTabs & Active Stage SSOT)

### القرار (Decision)
1. استخدام مكوّن `FolderTabs` القياسي المعتمد في المنظومة:
   - التبويب 1: الرئيسية (`dashboard`)
   - التبويب 2: التمام اليومي (`rollcall`)
   - التبويب 3: المرحلة الحالية (`current-stage` بعنوان ديناميكي "مرحلة YYYY/X")
   - التبويب 4: المراحل السابقة (`previous-stages` يعرض افتراضياً متبقيات المراحل مع فلتر لكامل المرحلة)
2. تخزين "المرحلة الحالية المعتمدة" كإعداد نظام في موديل `SystemSetting` بالمفتاح `STUDENTS_ACTIVE_STAGE`.
   - عند عدم وجود إعداد مسبق، يستعلم النظام عن أحدث مرحلة تجنيدية في جدول الطلاب (أعلى رقم دفعة `mrhla`) ويحددها تلقائياً.

### الأسباب (Rationale)
1. **مرجع موحد لكافة المستخدمين (SSOT):** منع تضارب الإحصائيات بين المستخدمين أو بين شاشات القيادة وضباط الشئون.
2. **سلاسة العرض:** التبويب الرابع يركز على المشاكل التشغيلية العالقة (المتبقيات وإيقاف الترحيل) دون إغفال القدرة على مراجعة أي مرحلة سابقة بالكامل عند التفتيش أو الاستعلام.
